# ADR-029: Document Generation & Template Management

**Status:** Accepted
**Date:** 2026-08-05

## Context

`types/document.ts`/`services/documentsService.ts` (an early phase, built for `DocumentsCard`) were pure in-memory mock fixtures with zero server or Wix integration and no API route at all — uploads vanished on server restart, "download" didn't exist as an action, and "Print" (`utils/print.ts`) was never PDF generation, just `window.open()`/`document.write()`/`window.print()`. Phase 24's own `ACTIVITY_EVENT_TYPES` registry already reserved `document.uploaded`/`document.generated`/`document.signed` with an explicit comment that no persisted document backend existed yet. RBAC had already declared `document.view`/`document.generate` permission keys back in Phase 22 — dead code, checked by no route, service, or component.

This phase builds the document infrastructure every future phase (e-signatures, notifications, portals, regulatory forms) will build on: reusable, versioned HTML+merge-field templates, a single orchestrating `DocumentService` that renders/stores/records every generated document, a provider-agnostic PDF renderer, and full RBAC/ActivityService integration.

**Explicitly out of scope this phase**: e-signatures, email delivery, notifications, family portals, OCR, document AI. A `signatureStatus` field exists on `CaseDocument`, always `null`, reserved for Phase 26 — the only forward-looking accommodation made, and it is inert.

## Architecture: three separated concerns, one clear owner each

1. **Templates are immutable once versioned.** `DocumentTemplate` (identity, in the `documentTemplates` Wix collection) and an append-only `DocumentTemplateVersion[]` (assembled at read time from a second collection, `documentTemplateVersions`) — mirrors `WorkflowTemplate`/`WorkflowTemplateVersion`'s exact two-collection split (Phase 14A/ADR-009) rather than inventing a new pattern. Editing a template's body always inserts a new version (`version + 1`); a version, once created, is never edited or deleted (`documentTemplatesService.ts` only ever calls `insertWixDataItem` against `documentTemplateVersions`). A `CaseDocument` permanently records the exact `templateVersion` it was generated from, so editing a template later can never retroactively change what a past generated document says — the same guarantee `Case.workflowSnapshot` already gives workflow templates.

2. **One orchestration layer: `services/documentService.ts` ("DocumentService").** All document-generation logic — resolving the template version, resolving merge fields, invoking the renderer, invoking storage, computing the checksum, persisting the `CaseDocument` row, and emitting the `ActivityEvent` — lives in exactly one place. No Route Handler and no UI component ever calls the renderer, the storage provider, or `activityService.record()` directly for a document action. Enforced structurally, not just by convention: `services/documentService.test.ts` walks the entire source tree and asserts only `documentService.ts` (and the two provider implementation files themselves) import `lib/puppeteerDocumentRenderer.ts`/`lib/vercelBlob/vercelBlobStorageProvider.ts` — mirroring `activityService.test.ts`'s own import-line immutability check from Phase 24.

3. **Rendering and storage are each provider-agnostic**, via a neutral interface (`lib/documentRenderer.ts`'s `DocumentRenderer`, `lib/documentStorageProvider.ts`'s `DocumentStorageProvider`) with exactly one real implementation each (`lib/puppeteerDocumentRenderer.ts`, `lib/vercelBlob/vercelBlobStorageProvider.ts`), imported directly wherever needed — matching `lib/paymentProvider.ts`/`lib/clover/cloverProvider.ts`'s actual precedent (there is no central `getPaymentProvider()` factory function anywhere in this codebase; Clover's own concrete provider object is imported directly by the checkout and webhook routes). Swapping either engine later is a new file implementing the interface plus updating two import lines in `documentService.ts` — no change to business logic, routes, or UI.

## Metadata vs. bytes

**Metadata** (template identity/versions, generated/uploaded document records) → **Wix Data**, matching ten phases of real, working precedent — including Phase 24's entire `ActivityEvent` audit trail. This is a deliberate divergence from the *original* project architecture doc (`docs/ARCHITECTURE.md`/ADR-001), which proposed a dedicated Postgres + S3/R2 service specifically for "compliance documents... and the audit trail." In practice, every phase since 15 (audit trail included) extended Wix Data instead — Postgres was never stood up. Reviving it now for structured metadata alone, when Wix Data has proven sufficient at real scale throughout this project's history, would be new, disruptive infrastructure for no concrete benefit. This ADR records that divergence explicitly rather than leaving it implicit.

**File bytes** (rendered PDFs, uploads) → a genuinely new piece of infrastructure: **Vercel Blob** (`@vercel/blob`), behind `lib/documentStorageProvider.ts`. This is the one part of ADR-001's original intent (an object store for the actual bytes) this phase does fulfill — just without the Postgres half. Chosen over S3/R2 for the simplest possible setup for a Next.js app (one env token, no bucket/IAM/region configuration).

**Correction made during implementation, not assumed in planning:** the original plan described minting a short-lived *signed* download URL for the browser to hit directly. Vercel Blob's SDK does support `access: 'private'` blobs, but there is no way to hand the browser a bare Blob URL and have it "just work" without the same read-write token — so this phase's `DocumentStorageProvider.downloadFile` instead returns raw bytes for the **download Route Handler** to stream back itself. The browser never receives a Vercel Blob URL of any kind — only Beacon's own `/api/cases/[caseId]/documents/[documentId]/download` endpoint, which re-checks authorization on every single request. This is a strictly stronger guarantee than a signed URL with an expiry window (there is no token to leak, ever), so this is a correction in the secure direction, not a regression from the plan.

## Invariants

- **A template version, once created, is never edited or deleted.** Editing a template's body always inserts a new `DocumentTemplateVersion` row; `documentTemplatesService.ts` never calls `updateWixDataItem`/`deleteWixDataItem` against `documentTemplateVersions`.
- **A generated document is immutable once it reaches a terminal status (`active`/`failed`).** A `pending` row is inserted the instant generation/upload starts — before rendering/storage even completes — so a mid-request crash during a slow render leaves a diagnosable row rather than silently losing the attempt. Its content fields (`storageKey`, `checksumSha256`, `fileSizeBytes`) are filled in exactly once, together, when the async work completes or fails, mirroring `PaymentRecord`'s own `pending -> succeeded/failed` update (which likewise fills in more than a bare status flag once the provider responds). A `pending` row has no real content yet, so this two-phase fill-in is not a violation of "immutable once created" — that guarantee begins once a row reaches `active`/`failed`. After that point, the only thing ever touched again is `status` (superseded via regeneration, archived, restored).
- **Regeneration targets the same or a newer template version, by explicit user choice — never silently "whichever is latest."** `DocumentService.generate(...)` takes an optional `templateVersion`; omitting it resolves to the template's current latest version at call time. Live-verified both ways: regenerating while explicitly pinning the original version, and regenerating against a version created after the original document.
- **A document-type or event identifier is a stable, machine-readable, dot-notation key, never a display string.** `DOCUMENT_TYPES` (`domain/documents/documentTypeRegistry.ts`) mirrors `ACTIVITY_EVENT_TYPES`'s exact convention: a `category` for broad UI grouping (the ten spec-named categories), a `displayName` never derived from the key, and the registry — not free text on a template — is the source of truth for what a template *is*.
- **An unrecognized merge-field token is a validation error, never empty output.** Rejected at template-save time (the exact offending token names listed) and, as a defensive backstop, at render time (`mergeTemplate` throws rather than substituting blank — live-verified). A *recognized but reserved* field (no backing data source — either the feature doesn't exist in Beacon at all, like funeral-service scheduling, or this specific case/organization simply has no value, like a case with no `CaseOrder` yet) is different from an unrecognized one: it resolves to the visible `[Not available]` placeholder, never a silent blank.
- **Every document-affecting action emits its `ActivityEvent`(s) from inside `DocumentService`**, using the existing `record()`/`ActivityContext`/correlationId machinery — never a raw payload constructed at a route or UI call site.

## Document taxonomy and merge-field catalog

`domain/documents/documentTypeRegistry.ts`'s `DOCUMENT_TYPES` is a controlled, dot-notation registry (`contract.funeral`, `authorization.cremation`, `financial.receipt`, `obituary`, `internal.checklist`, ...) covering all ten spec-named categories, extensible the same way `ACTIVITY_EVENT_TYPES` is — a future document type is a new registry entry, never a data-model change.

`domain/documents/mergeEngine.ts`'s `MERGE_FIELD_CATALOG` is the strongly-typed merge-field system: every entry carries an `identifier`, `displayName`, `dataType`, `description`, `exampleValue`, `category`, and a `resolve` function, plus a `wired` flag distinguishing "has a real data source" from "reserved." `case.service.date`/`case.service.location` are deliberately `wired: false` — `types/case.ts` has no service-scheduling fields at all (funeral/service scheduling is a named, unbuilt V2 candidate in `docs/ROADMAP.md`) — reserving the catalog slot now means a future scheduling phase only needs to flip `wired` and supply a real `resolve`, never a merge-engine or template-authoring change. `financial.total`/`financial.balanceDue` read from `CaseOrder` (Phase 19C); `organization.documentFooter` finally consumes `OrganizationBranding.documentFooter` (Phase 20, built, never consumed until now).

Template bodies are HTML fragments with `{{namespace.field.path}}` tokens — deliberately **not** a general templating language (no loops/conditionals/arbitrary logic via Handlebars/Mustache/EJS), both for simplicity and because a template body eventually reaches a headless-Chromium render step, where arbitrary logic would be a real attack surface.

## Security: sanitization and network lockdown

Template bodies are sanitized on every save (`domain/documents/sanitizeTemplateBody.ts` — a narrow, hand-rolled allowlist stripping `<script>`, inline event-handler attributes, `javascript:` URLs, and `<iframe>`/`<object>`/`<embed>` tags, deliberately not a new dependency for this constrained, well-understood input domain). This matters even though template authors are always trusted org staff, for two independent reasons: a compromised or malicious org account should never be able to embed executable content, and the headless-Chromium render step executing attacker-controlled HTML server-side would be a genuine SSRF/code-execution risk (e.g. an `<img>` tag probing an internal address). As defense-in-depth beyond sanitization, `lib/puppeteerDocumentRenderer.ts` intercepts every network request during rendering and aborts anything that isn't a `data:` URI — a malicious template's external resource reference simply never resolves, network-lockdown enforced by the renderer itself, independent of whatever sanitization already caught.

Uploads are capped at 15MB with an allowlist of PDF/JPEG/PNG/DOCX, enforced server-side (never trusting client-side validation alone, matching `lib/paymentFieldGuard.ts`'s existing discipline).

## PDF rendering: headless Chromium, not a component-based library

**Chosen: server-side HTML+CSS rendering via headless Chromium** (`puppeteer-core` + `@sparticuz/chromium` for serverless deployment; a local Chrome install via `PUPPETEER_EXECUTABLE_PATH` for development — never guessed or hardcoded to one OS's install path). The exact same merged HTML that renders as a template's live in-browser preview also produces the final PDF — true WYSIWYG parity, full CSS page-layout support, full Unicode/font fidelity (live-verified with a multi-page body containing Café/Müller/日本語 text, rendering correctly).

**Considered and rejected: `@react-pdf/renderer`.** Lighter and faster to cold-start, but its own constrained component model (View/Text/Page, no flexbox `gap`, manual font embedding) means a template author's preview is never pixel-identical to the actual PDF, and it would hit real layout ceilings for the multi-page legal-document complexity this system needs to grow into (e-signatures, regulatory forms). The heavier deployment cost of headless Chromium is an accepted trade-off: generation is on-demand/async (never blocks page render), volume is inherently low, and `@sparticuz/chromium` is the standard, widely-used mitigation for exactly this Vercel + Puppeteer combination.

## Data model

See `types/documentTemplate.ts` and `types/caseDocument.ts` for the full shapes. Notable fields: `CaseDocument.checksumSha256` (SHA-256 of the exact stored bytes, computed once at storage time, never trusted from a client — supports future tamper/corruption detection with no schema change); `CaseDocument.signatureStatus` (reserved for Phase 26, always `null` this phase); `CaseDocument.supersedesId` (the row a regeneration replaces — that row's own `status` flips to `superseded`, never deleted, since past generated documents, including old contract/permit versions, must remain individually downloadable for legal/audit reasons).

## Permissions

`document.view`/`document.generate` (Phase 22, previously dead) are finally wired to real routes. Four new keys: `document.upload`, `document.archive` (case-scoped document lifecycle), `document.template.read`, `document.template.manage` (org-wide Template Library, mirroring `audit.read`/`audit.export`'s read/manage split). `readOnly` deliberately does **not** get `document.upload` despite `document.view`'s own tier otherwise including it — uploading is a write action, and `readOnly` is the one role in the catalog whose entire permission list was, until now, exclusively read/view actions; granting it upload would have been the first write action that role ever held, contradicting its own name. Total permission count moves from 24 to 28.

Case-scoped document routes gate on `document.view`/`document.generate`/`document.upload`/`document.archive` as a **real, intentional** permission check — unlike Phase 24's Case Activity tab (which reuses `requireAuthorizedOrganization` alone, since no separate case-activity permission ever existed). `document.view`/`document.generate` already existed as keys distinct from `case.read` before this phase, so reusing them here is wiring up a pre-existing, deliberate gate, not inventing a redundant one.

**Correction made after the UI landed:** `GET /api/document-templates` and `POST /api/document-templates/[templateId]/preview` were originally built identity-mode-only (`requireIdentitySession`), matching every other RBAC-touching org-wide route (`/api/rbac/*`, `/api/activity`) — a deliberate pattern, since those routes only ever have a UI consumer on an identity-mode-gated Settings page. But the case-scoped **Generate/Regenerate Document dialog** (on the universal Case Detail page, which — like Phase 24's Activity tab — must work under every `AUTH_ADAPTER`) reads both of these same two routes to populate its template dropdown and render its live preview. Discovered by driving the dialog end-to-end under `AUTH_ADAPTER=mock`: the dropdown stayed empty and Preview 401'd. Both routes were switched to the dual-mode `requireAuthorizedOrganization` pattern (identical to every case-scoped document route), while template *creation/editing/cloning/archiving* — reachable only from the identity-mode-gated Template Library page — correctly stayed identity-only. `CaseDocumentsTab.tsx` itself was also corrected: it had hard-depended on `GET /api/rbac/my-permissions` (identity-mode-only, same reasoning) for its own action-button gating, which left every mock-mode user staring at "You don't have access to this case's documents" once that query's retries exhausted. Since that endpoint's own doc comment already establishes it as UI-gating convenience, never the real authorization decision, the fix was to treat a still-loading or unavailable permissions query as *permissive* (every action button shown, exactly as `document.view`/`document.generate`/etc. already re-check server-side on the real routes) rather than *restrictive*.

**Live-data corollary:** the real `managed-cremations` organization's `rolePermissions` collection was seeded once, in Phase 22, before these four Phase-25 permission keys existed. Adding a permission to `domain/rbac/defaultRoles.ts` does not retroactively backfill an already-provisioned organization's rows — `seedPlatformDefaultRoles` had to be re-run once against live Wix (safe and idempotent: it inserts only missing `(roleKey, permissionKey)` rows, no-oping on an existing id) to grant `document.upload`/`document.archive`/`document.template.read`/`document.template.manage` to the organizations already live before this phase shipped. Any future organization provisioned after this phase picks these up automatically via the same seeding call `organizationProvisioningService.ts` already makes.

## Live Wix verification

A disposable pair of throwaway organizations + cases, `DATA_ADAPTER=wix`, via the real service functions: created the three new collections (index cap re-confirmed empirically at `{"regular":3,"unique":1,"total":4}` on all three, exactly matching every prior collection's own cap); stored and re-fetched a realistic multi-KB template body, byte-for-byte identical; confirmed unknown-merge-field rejection; generated a real PDF via genuine headless Chromium (Unicode/multi-page verified separately in the unit suite); regenerated once pinning the original template version and once resolving the newer one, confirming version/templateVersion tracking and the supersession chain; confirmed a superseded row's content fields are byte-identical to what they were before supersession; downloaded and archived; confirmed all seven expected `ActivityEvent` types recorded with correct correlationId sharing; confirmed cross-tenant isolation for both templates and documents, including a case genuinely sharing the identical `caseId` string across two organizations. Every row created was deleted afterward; a final query confirmed zero rows remained in either organization across all three new collections plus `activityEvents`.

**One honestly-documented gap:** the REST endpoint for creating a secondary (non-unique) index on an existing Wix Data collection could not be determined this session — several plausible URL/verb combinations were attempted and each returned a 404 or a generic "partial update" error, unlike collection creation itself (which worked on the first correctly-shaped request). The index *cap* was still re-confirmed empirically (via the `capabilities.indexLimits` field every collection-creation response includes), which was the substantive platform constraint this phase needed to verify; the three new collections' secondary indexes should be added via the Wix dashboard's collection editor, or the correct REST shape identified in a future session, before these collections see meaningful production query volume.

## Deferred

- E-signatures, email delivery, notifications, family portals, OCR, document AI — explicitly out of scope (see Context). The `signatureStatus` reservation is the only forward-looking accommodation, and it is inert.
- Migrating the four Phase 24-adjacent legacy audit writers is unaffected by this phase (unrelated).
- A richer WYSIWYG template body editor — a plain sanitized text/HTML editor is a deliberate scope-limiting choice this phase.
- Background/queued generation — this phase's generation is synchronous request/response, acceptable at expected volume.
- **`BLOB_READ_WRITE_TOKEN` is not provisioned in local development** — the same deferred-credential posture as Clover's sandbox merchant account in Phase 19B. `lib/vercelBlob/vercelBlobConfig.ts`'s `getVercelBlobToken()` throws a clear, named error (never a generic failure) when it's unset; `DocumentService.generate()`/`upload()` catch this and persist the `CaseDocument` row as `status: 'failed'` rather than leaving it ambiguously `pending` or crashing the request — verified live against the real `managed-cremations` organization (merge engine and headless-Chromium rendering both succeeded; only the storage step failed, exactly as designed). Provisioning a real Vercel Blob store and setting this env var is required before generation/upload/download work end-to-end in any environment.
