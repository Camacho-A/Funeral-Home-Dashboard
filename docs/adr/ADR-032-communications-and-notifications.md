# ADR-032: Communications & Notifications

**Status:** Accepted
**Date:** 2026-08-04

## Context

Every phase since Phase 20 left a spot reserved for this moment without building it: `types/activityEvent.ts`'s `ActivityEventCategory` already included `'notifications'`, unused by any event type and already wired into display code (`lib/wixActivityEventMapper.ts`, `domain/activity/activityDisplay.ts`'s `notifications: 'Notifications'` label). `lib/schedulingNotifier.ts` (Phase 27) defined a complete `SchedulingNotifier` interface with zero concrete implementation and zero call sites. `lib/signatureNotifier.ts` (Phase 26) had a concrete, wired implementation, but only for the external signer's own email — nothing told *staff* when a document got signed. Every business service had zero in-app notification concept at all.

This phase builds the platform that reserved spot was anticipating: a place notifications live, get delivered, and get read — independent of `ActivityService`, which remains the one real audit trail.

**A load-bearing scope decision, stated up front:** `IdentityMessageSender` (password reset, email verification, invitation, MFA recovery codes) and the *external-signer* side of `SignatureNotifier` are untouched by this phase. Those are mandatory, unpreferenced, security-critical transactional messages to people who may have no Beacon account at all — they share nothing with an opt-in-able, preference-respecting, in-app-visible "notification." `NotificationService` is for **staff-facing** notifications about business events.

**Twelve architectural refinements were requested before implementation began**, the most consequential: a hard separation between `Notification` ("what happened") and `Delivery` ("how it was sent"), with fully independent lifecycles; a stable category registry aligned with `ActivityEventCategory`'s own existing naming (`scheduling`, not `appointment`); a generalized `entityType`/`entityId` reference rather than a case-specific field; channel-agnostic templates; and an unread badge that is always a live query, never a separately-maintained counter. These are documented as their own sections below.

## Architecture: Notification and Delivery are two fully independent entities

**`Notification`** — what happened. Content (`title`, `body`), `category`, the originating domain reference (`entityType`/`entityId`), and an own lifecycle describing whether the notification itself currently exists/is visible: `Draft → Queued → Active → Archived`, or `Cancelled` (only reachable pre-`Active`). This lifecycle has nothing to do with any individual person having read it.

**`NotificationDelivery`** — how it was sent. One row per `(recipient, channel)` — today: `in_app` and `email`; reserved, not implemented: SMS, push, webhooks. Its own independent lifecycle: `Pending → Sent → Delivered → Read`, or `Failed`. A `Notification` can reach `Active` while individual `Delivery` rows are still `Pending` or have reached `Failed`; a `Delivery` reaching `Read` never changes the `Notification`'s own status at all — live-verified directly (see "Live Wix verification" below).

**`NotificationRecipient`** — the immutable resolution snapshot. Resolved exactly once, at creation time, from whichever recipient scope was requested (`individual`/`role`/`organization_wide`/`case_participants`), and never recomputed. A role/organization-wide notification is a frozen snapshot of who mattered *then*; live-verified: a membership added to a role after a notification was created did not retroactively appear in that notification's own recipient list. `NotificationRecipient` carries two denormalized convenience fields — `readAt`/`archivedAt` — set by the same `NotificationService` call that also transitions the recipient's in-app `Delivery` to `Read`. This is not a second state machine; it exists purely so the unread badge and "hide archived" filter are a single indexed query, never a join.

**Notification Category registry — aligned with `ActivityEventCategory`.** `domain/notifications/notificationTypeRegistry.ts`'s `NotificationCategory` is deliberately `'scheduling'`, not `'appointment'` — the exact value `ActivityEventCategory` already reserved in Phase 27, so a scheduling-triggered notification and its corresponding `ActivityEvent` agree on vocabulary. Display names live separately (`NOTIFICATION_CATEGORY_LABEL`), never derived from the machine key.

**Templates produce structured, channel-agnostic content.** `domain/notifications/notificationTemplateRegistry.ts` is keyed by `notificationType` only, never `(notificationType, channel)`. `resolveNotificationContent()` returns `{ title, body, actionUrl }` — `emailChannel.ts` turns that into a subject + HTML body; `inAppChannel.ts` stores it verbatim. A recognized-but-unreferenced token catalog (`assertOnlyRecognizedTokens`) mirrors `mergeEngine.ts`'s own "no silently-accepted unrecognized identifier" discipline, deliberately without reusing the merge engine itself.

## One orchestration layer, no exceptions

`services/notificationService.ts` is the only thing any caller — a route, `SignatureService`, a future module — is ever allowed to call. It alone imports the recipient resolver (`services/notifications/recipientResolver.ts`), both channels (`emailChannel.ts`/`inAppChannel.ts`), and the six `recordNotificationX` activity helpers; it alone performs recipient resolution, delivery dispatch, and lifecycle transitions. Structurally enforced by `notificationService.test.ts`'s own source-tree-walk "orchestration boundary" describe block, mirroring `schedulingService.test.ts`'s exact pattern: five assertions (recipient resolver, email channel, in-app channel, the six activity helpers, and no file other than `notificationService.ts` writing to any of the five new collections directly).

`RecipientResolverError` is caught inside `createNotification` and rewrapped as `NotificationServiceError` rather than left to propagate — `recipientResolver.ts`'s own error type must never leak to a caller who would otherwise need to import that module directly just to catch it, which would itself violate the import boundary. Discovered during implementation and fixed before this phase's structural test was allowed to pass.

## Recipient resolution: `case_participants` is real but not implemented this phase

`services/notifications/recipientResolver.ts` resolves `individual`/`role`/`organization_wide` against `services/membershipService.ts`'s real identity-mode `Membership` model. **`case_participants` is a genuine value in `RecipientScope`, kept for future-readiness, but throws a clear `RecipientResolverError`:** `Case.assignedStaffId`/`intakeOwnerId` reference `StaffProfile.id` (a separate, pre-Identity-model, mock-only concept), not a real `Identity.id`/`Membership.id`, and no mapping between the two exists anywhere in this codebase — the same gap `docs/AUTHENTICATION.md`'s own Known Limitations section already names. Presented to the user as a genuine recipient-resolution ambiguity before implementation continued (per this phase's own approved-plan instruction); the user selected deferring it, matching a future `external` (family/next-of-kin) scope's own not-yet-implemented treatment — never a silent, invented bridge.

## Bounded integration surface: Signature only, this phase

The approved plan named three real production integrations: Scheduling, Signature, Task. Implementation surfaced that **two of the three hit unresolvable recipient-resolution gaps, and both were explicitly deferred by the user rather than worked around:**

- **Scheduling** — `lib/schedulingNotifier.ts`'s Phase 27 interface (`notifyAppointmentCreated`/`notifyAppointmentRescheduled`/`notifyAppointmentCancelled`) carries only display strings (`caseDisplayName`, `appointmentTitle`, `startAt`) — no recipient identity field at all. The natural correct recipient is the case's assigned staff, which requires exactly the `case_participants` scope just deferred above. Presented to the user as a second occurrence of the same class of gap; the user chose to leave `SchedulingNotifier` exactly as Phase 27 shipped it — interface only, zero concrete implementation, zero call sites, unchanged by this phase.
- **Task** — `CaseTask.assigneeStaffId` is the identical `StaffProfile.id`, not an `Identity.id`, with the identical absence of any mapping. Presented to the user a third time; the user again chose to defer rather than invent a `StaffProfile`→`Identity` bridge out of scope for this phase.
- **Signature** — the one integration with a real, already-available recipient: `SignatureRequest.requestedBy` (captured as `ctx.actorIdentityId` at request-creation time) is a genuine `Identity.id`, no bridge needed. `services/signatureService.ts`'s `completeSignatureRequest`/`declineSignatureRequest` each gained one **additive** call to `notificationService.createNotification` — never replacing the existing external-signer email (`signatureNotifier.notifyCompleted`/`.notifyDeclined`, still fired exactly as before), targeting the requesting staff member with `signature.completed`/`signature.declined`. A small local `getCaseForNotification` reader was added to `signatureService.ts`, mirroring `documentService.ts`'s own `getCaseForMerge` pattern exactly (`services/casesService.ts` is a client-fetch service, not callable from server-side orchestration mid-request).

`Case`/`Payment`/`Document`/`Organization`/`System` notification types remain fully defined in the registry, fully covered by unit tests and the UI — no production emitter for any of them ships this phase, a named deferral matching the plan's own original scope language.

## Unread badge: always a live query, never a counter

`getUnreadCount` queries `NotificationDelivery`'s denormalized `identityId` field directly — `(organizationId, identityId, channel: 'in_app', status != 'read')` — never joining through `NotificationRecipient` and never maintaining a stored count. See "Live Wix verification" below for the empirical `COUNT`-capability finding this query's implementation is based on.

## Preferences: shaped to add per-category overrides later, without a migration

`NotificationPreference` implements only a global `emailEnabled`/`inAppEnabled` toggle this phase — a missing row resolves to both channels enabled by default, a synthetic unpersisted view, never eagerly seeded. The shape is deliberately ready for a future `categoryOverrides` field via the same "resend the full field list via `PUT /v2/collections`" mechanism this codebase has already used repeatedly (`paymentRecords`, `organizations`, `organizationMemberships`) — never a redesign or a migration for existing rows.

## Live Wix verification

Five new collections (Collections 42–46: `notifications`, `notificationRecipients`, `notificationDeliveries`, `notificationDeliveryAttempts`, `notificationPreferences`) were created live via the proven `POST /wix-data/v2/collections` shape, and all nine planned indexes created via `POST /wix-data/v2/indexes` and confirmed `ACTIVE`.

**A new limitation was discovered while creating them: Wix Data compound indexes cap at 3 fields.** The originally planned 4-field unread-badge index — `(organizationId, identityId, channel, status)` on `notificationDeliveries` — was rejected (`WDE0080: fields has size 4, expected 3 or less`). Redesigned live to a 3-field `(organizationId, identityId, status)` index, with `channel` filtered in application code as a narrowing rather than an index boundary — the same "index narrows, application code is the correctness boundary" discipline `activityService.ts` already established for its own multi-filter queries.

Exercised through the real `notificationService.ts`/`signatureService.ts` functions against `DATA_ADAPTER=wix`, using Manor's Cremation's real, already-migrated (Phase 21) identities and memberships (read-only against `Membership`; every `Notification`/`Recipient`/`Delivery`/`Attempt`/`Preference` row this phase's verification created was its own new, disposable data):

- An individual-scope notification confirmed one `NotificationRecipient` and one `NotificationDelivery` row per enabled channel (`email` reaching `sent`, `in_app` reaching `delivered`), both `NotificationDeliveryAttempt` rows recording success, and the `Notification` reaching `active` — all live.
- Marking the in-app delivery read confirmed only that `Delivery` row and the `NotificationRecipient.readAt` field changed; the `Notification`'s own `status` was confirmed unchanged immediately afterward via a fresh read — the two lifecycles' independence is not just unit-tested, it is live-verified.
- A role-scope notification confirmed it fanned out to exactly the one currently-active membership holding that role — matching the expected set computed independently from the same live `Membership` rows.
- A disabled-`emailEnabled` preference correctly produced zero `email` `Delivery` rows for a subsequent notification, confirmed live, then restored.
- A draft notification was confirmed cancellable; cross-tenant isolation was confirmed (a second organization's notification never appeared in the first organization's inbox or org-wide log).
- All six `notification.*` `ActivityEvent` types (`created`/`sent`/`delivered`/`read`/`failed`/`cancelled`) were confirmed recorded live, each sharing the correlationId of the request that produced it.
- **`COUNT` capability confirmed reachable**, via a dedicated `POST /wix-data/v2/items/count` endpoint (`{ dataCollectionId, query: { filter } }` → `{ totalCount }`) — a genuinely different endpoint from `/wix-data/v2/items/query`, not documented anywhere in this codebase before this phase. **However, it was empirically observed to return a stale/inflated total shortly after a rapid sequence of writes and deletes against the same rows** (a direct test creating exactly two matching, freshly-inserted rows with zero pre-existing ones — independently confirmed via a full state re-query — returned `totalCount: 4` from the count endpoint). Given this, `getUnreadCount` deliberately keeps its existing bounded fetch-and-count implementation (via the regular, observed-consistent query endpoint) rather than switching to the faster but inconsistency-prone dedicated count endpoint. Documented as a Known Limitation in `docs/WIX_DATA_SCHEMA.md`, not assumed away.
- One non-reproducing anomaly was investigated directly: a single role-scope notification's email channel appeared to produce no `Delivery` row in one run. A direct, isolated reproduction attempt using the identical identity and an individual scope succeeded cleanly with both channels dispatched — concluded to be a transient write/consistency blip (consistent with this project's own previously-documented Wix Data rate-limit/eventual-consistency findings), not a reproducible code defect.
- **`seedPlatformDefaultRoles('wix')` hit the same `HTTP 429` rate-limit Phase 27's own closeout found** re-running the full seed. Resolved via the identical targeted, quota-efficient fix: query each role's existing `rolePermissions` grants first, insert only the genuinely missing keys. Final live counts, confirmed via a fresh query after reseeding: administrator 42, manager 36, funeralDirector 25, arranger 15, officeStaff 13, accounting 9, readOnly 10 — each exactly Phase 27's own total plus that role's notification.* tier.
- Every disposable row this verification created — across all five new collections — was deleted afterward; a final query confirmed zero residual rows in four of the five collections, with exactly one legitimate (non-disposable) `NotificationPreference` row intentionally left in place, reflecting the real admin identity's own restored preference state.

## Permissions

Four new keys: `notification.read`, `notification.send`, `notification.manage`, `notification.admin` (reserved for a future org-wide notification policy surface). Tiered by mirroring existing precedent: `notification.read` mirrors `audit.read`'s own broader tier (administrator, manager, funeralDirector, accounting, readOnly); `notification.send` mirrors `document.generate`/`schedule.create`'s tier (every role except accounting, readOnly); `notification.manage`/`.admin` mirror `document.template.manage`/`signature.manage`'s narrower tier (administrator, manager only). Total permission count moves from 38 to **42**. The personal inbox (own notifications, unread count, mark-read/archive, own preferences) requires no permission beyond authentication — scoped entirely by the caller's own identity, matching the approved plan's explicit "no permission needed for your own inbox" instruction.

## Deferred

- SMS, push, voice, webhooks, workflow automation, family (external/next-of-kin) notifications, a real third-party email provider, marketing email, AI-generated messaging — explicitly out of scope, each a named extension point.
- `SchedulingNotifier` concrete delivery and `CaseTask`-assignment notifications — both blocked on the same `StaffProfile`→`Identity` mapping gap `case_participants` already names; deferred by explicit user decision rather than bridged.
- `Case`/`Payment`/`Document`/`Organization`/`System` notification types — fully defined, tested, and visible in the UI, with no production emitter this phase.
- Per-category notification preferences, digest batching, quiet hours — schema-only reserves; no UI control and no enforcement logic this phase.
- A real transactional email provider — identical, already-accepted posture to `IdentityMessageSender`'s own gap.
