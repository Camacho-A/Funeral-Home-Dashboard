# ADR-026: Role-Based Authorization Architecture

**Status:** Accepted
**Date:** 2026-07-27 (architecture); first security-correction round closed 2026-07-28; second security-correction round (lock lease/fencing, provisioning integration) closed 2026-07-29; third security-correction round (write-claim stale-writer rejection) closed 2026-07-30.

## Context

Every authorization decision Beacon has made through Phase 21 has been a direct role-name comparison: `role === 'owner' || role === 'administrator'` (`lib/auth/authorize.ts`'s `hasAdminTierMembership`), the same pattern repeated in `services/organizationProvisioningService.ts`'s admin-count check and `app/api/auth/invitations/route.ts`'s invite gate. This is inflexible in exactly the way the phase spec names: adding a new tier of access means finding and updating every hardcoded comparison, and an organization can never customize what one of its own roles is allowed to do. This phase introduces a centralized permission model — `Permission` → `Role` → `Membership` — and migrates every existing role comparison to resolve through it, **without changing what any of those comparisons decide**.

## Identity, Membership, and now Authorization are three separate layers

Phase 21's ADR-025 established Identity ("who") and Membership ("what organization, what role") as deliberately separate concepts. This phase adds the third: Authorization ("what may that role actually do"), resolved by `services/permissionService.ts`/`services/authorizationPolicyService.ts` from `Membership.role`, never inlined into a business decision directly. `services/roleService.ts` owns role *lifecycle* (creating, cloning, editing, assigning); `services/permissionService.ts` owns role → permission *resolution* and its cache; `services/authorizationPolicyService.ts` is the only layer any Route Handler or business service should call — `canEditCase`, `canCollectPayment`, `canManageOrganization`, and so on, each a named function wrapping exactly one permission check. No business service compares a role name, and none inspects `AUTH_ADAPTER` — the same invariant Phase 21 already held.

## Widening `role` from a closed union to a plain key — the load-bearing compatibility decision

`types/membership.ts`'s `Membership.role` and `types/authorization.ts`'s `AuthorizationContext.role` were both typed as a closed five-value union (`'owner' | 'administrator' | 'caseManager' | 'staff' | 'readOnly'`). The phase spec's seven named roles (Administrator, Manager, Funeral Director, Arranger, Office Staff, Accounting, Read Only) are a different vocabulary, and organizations must additionally be able to create their own custom roles with generated keys — neither fits inside a compile-time-closed union. Both fields are widened to plain `string`, documented as "a role key resolved through `services/permissionService.ts`, never compared directly." This is the one type change touching existing, already-shipped fields; every other change in this phase is additive.

**Why this doesn't change any existing behavior:** `domain/rbac/legacyRoleAliases.ts` maps each of the five legacy values onto one of the seven Phase 22 default role keys — `owner`/`administrator` → `administrator`, `caseManager` → `funeralDirector`, `staff` → `officeStaff`, `readOnly` → `readOnly` — and `resolveRoleForKey` applies this alias before any lookup. No existing `Membership`/`OrganizationMembership` row's `role` value was migrated or needs to be; every value already written continues to resolve to the exact permission set it always implied. `lib/wixMembershipMapper.ts`'s `isValidRole` was relaxed from the closed list to "non-empty string" for the same reason — the full valid set (five legacy values, seven default keys, plus any organization's custom-role keys) is dynamic and per-organization, not something a synchronous mapper function can check against a compile-time list; semantic validation ("does this key actually resolve for this organization") moved to `resolveRoleForKey` and `RoleService.assignRole`, where a real lookup is possible.

## Seven platform-default roles, seeded once, enabled per organization

`domain/rbac/defaultRoles.ts` defines the seven roles' names, descriptions, and permission sets across **22 permissions spanning 10 resources** (`case`, `caseOrder`, `workflow`, `payment`, `serviceCatalog`, `document`, `report`, `organization`, `user`, `settings` — `domain/rbac/permissionCatalog.ts`) — the single source of truth seeded into the `roles` collection (`organizationId: null`, `isSystemDefault: true`) by `RoleService.seedPlatformDefaultRoles`, an idempotent, global bootstrap (a no-op in mock mode, where they're already statically seeded in `services/__mocks__/rbacFixtures.ts`). Every organization gets its own `organizationRoles` roster row per default role at creation time (`RoleService.seedDefaultRoles`) — a materialized "which roles are available here" list, rather than a filtered query across the shared `roles` collection, so the Organization Roles Page and permission resolution both read one collection scoped by `organizationId` instead of reasoning about `organizationId: null` meaning "global."

**Cloning, not editing, is how a default role is customized.** `RoleService.cloneRole` copies a source role's permission set into a brand-new `roles` row scoped to the requesting organization (`isSystemDefault: false`) and adds its own `organizationRoles` entry — the source role, default or custom, is never modified. `RoleService.updateRole`/`deleteRole` both refuse outright (a thrown `RoleServiceError`, surfaced as HTTP 409) if the target role's `organizationId` is `null` — "Platform default roles remain immutable" is enforced in code, not only by convention.

## Security-correction round (2026-07-27/28)

Phase 22 was conditionally approved pending five corrections, all closed before this ADR's final acceptance. Each is documented in depth in its own subsection below; this is the summary.

1. **The last-administrator invariant was not concurrency-safe.** The original implementation read the organization's active memberships, decided whether a change was safe, and only then wrote — a classic time-of-check-to-time-of-use race. Two simultaneous requests could each observe "another administrator still exists" before either had written, and both proceed, leaving zero. Fixed with a durable, per-organization lock (`services/organizationLockService.ts`) plus a single, unified admin-count check (`services/roleService.ts`'s `countActiveAdminTierMembers`) run *inside* that lock by every mutation that can affect who counts as an administrator.
2. **The permission cache was only correct for a single application instance.** Removed entirely — see "No cross-request permission cache," below.
3. **Seeding needed durable idempotency under concurrency**, not just "already seeded, skip" read-before-write. Fixed with deterministic ids (`domain/rbac/deterministicIds.ts`) and insert-then-treat-conflict-as-success semantics.
4. **Fail-closed behavior for missing/foreign/malformed roles and assigned-role lifecycle events needed explicit tests**, not just an implicit assumption. All were already fail-closed by construction; this round added the tests proving it and closed one real remaining gap (permission removal from an *assigned* role — see below).
5. **A permission/resource count discrepancy** (a report incorrectly said "8 resources") is corrected here: **22 permissions, 10 resources.**

### The last-administrator invariant, made concurrency-safe

Every mutation that can remove someone's admin-tier access — `assignRole`, `removeRole`, `updateRole` (removing `organization.manage` from an assigned role), `deleteRole`, and the new `setMembershipStatus` (disabling/removing an admin-tier member) — now runs inside `services/organizationLockService.ts`'s `withOrganizationRoleLock(organizationId, ...)`, and checks the resulting admin count *inside* that lock via a single shared helper, `countActiveAdminTierMembers`, which accepts a `simulation` describing the hypothetical change (a different role for one membership, an excluded membership, or a role's hypothetical post-edit permission set) and counts how many active members would still hold `organization.manage` if that change were applied. If the answer is zero, the entire mutation is refused before anything is written.

## Second security-correction round (2026-07-29)

The first round's lock had a flat, non-renewable 10-second TTL — flagged as a production-integrity gap: a protected operation that legitimately runs longer than 10 seconds (a realistic outcome under Wix Data rate limiting, which this project hit live, repeatedly, during the first round's own re-seeding verification) could have its lock silently reclaimed by a second caller while the first was still executing, defeating the lock's entire purpose. Two corrections:

1. **The lock became a renewable lease with ownership-token validation and a monotonic fencing token** — see "The lock is now a renewable lease," below.
2. **RBAC seeding is now wired into organization provisioning itself**, not left as a manual, one-off step Manor's Cremation happened to receive by hand — see "Organization provisioning now seeds the RBAC roster automatically," below.

### The lock is now a renewable lease, not a fixed-TTL lock

`services/organizationLockService.ts`'s `withOrganizationRoleLock` still acquires the same way (insert a row whose id is the `organizationId` — the one primitive this project has actually confirmed, per ADR-025's "inserts and catches the 409 on a race"), but ownership is now a **lease**, not a one-shot lock:

- **Renewal.** The moment the lease is acquired, a background heartbeat begins, renewing (extending `expiresAt`) every `LEASE_RENEW_INTERVAL_MS` (3 seconds by default — a third of the 10-second `LEASE_TTL_MS`, so at least two renewal attempts land inside every lease period before it could actually lapse). A protected operation that runs past the original TTL simply keeps its lease alive through renewal, rather than losing it.
- **Ownership token (`lockToken`).** Unchanged in spirit from the first round: a fresh random value per acquisition. Renewal and release both re-read the stored row and act *only* if its `lockToken` still equals the caller's own — never a blind write.
- **Fencing token (`fenceToken`, new).** A monotonically increasing integer on the `organizationRoleLocks` row, incremented every time the lock is acquired fresh or reclaimed from a stale holder. Checked alongside `lockToken` on every renewal and release (`isCurrentOwner`), and exposed directly to the protected operation: every one of `RoleService`'s five guarded mutations calls `assertFenceStillCurrent(handle, dataAdapterMode)` immediately before its actual write (right after the admin-count check, which is the part most likely to take a while — one Wix Data read per active membership). This is the second, independent signal that catches supersession even in the — astronomically unlikely, but not assumed away — case of a reused `lockToken` value.
- **Fail-closed renewal.** If a renewal attempt ever finds the stored row's `lockToken`/`fenceToken` no longer match (a newer owner has already reclaimed the lease), it throws `LockLeaseLostError`. `withOrganizationRoleLock` propagates this as the *overall* result of the call — even if the wrapped operation's own logic had already produced what looks like a successful result, that result is discarded and the error is thrown instead. A caller must never trust a result produced after its lease was lost, full stop.
- **Stale recovery is structurally unchanged.** A lease only ever lapses if its holder stops renewing it, which is exactly what a crashed or hung process does automatically — no separate crash-detection mechanism is needed. On contention, an expired lease is reclaimed immediately (its fence token incremented) rather than waited out.
- **Configurable for testing.** `withOrganizationRoleLock` accepts optional `{ leaseTtlMs, renewIntervalMs }` overrides, defaulting to the production values (10000ms / 3000ms) — used to make the "an operation runs longer than the lease TTL" scenario reproducible in milliseconds rather than requiring multi-second tests.

**What this does and does not guarantee.** Renewal and release are read-then-conditionally-act, not a true atomic compare-and-swap (which would require Wix Data revision support this project has not independently confirmed). The realistic race window this leaves is small — bounded by the gap between a renewal's read and its write — and, critically, is always caught before a protected write completes: either the periodic renewal heartbeat detects supersession and fails the whole operation closed, or the fencing check immediately before the actual write does. What's guaranteed: an operation that keeps renewing on schedule never has its lease reclaimed out from under it; an operation whose lease *is* reclaimed (because it stopped renewing, e.g. a crash) can never have its stale result trusted, because either the heartbeat or the fencing check will have already thrown by the time that result would otherwise be returned.

See `services/organizationLockService.test.ts`'s "renewable lease" tests:
- an operation deliberately running longer than the original lease TTL completes safely via renewal;
- a competing acquisition during that long operation is refused until the first genuinely releases (the exact race this round closes — without renewal, the competitor would have reclaimed at the original TTL mark while the first operation was still running);
- an owner whose lease has been reclaimed fails the same ownership check release/renewal rely on, and cannot disturb the new owner's still-active lease;
- a lease lost mid-operation fails the *overall* call closed, even though the wrapped operation's own logic "succeeded";
- a genuinely abandoned lease (simulating a crashed process — no renewal ever occurs) is reclaimed once it expires, with the fence token advancing past the abandoned holder's.

See `services/roleService.test.ts`'s "concurrency: the last-administrator invariant under simultaneous requests" — two administrators simultaneously demoting each other via `Promise.allSettled`; exactly one succeeds, the other is rejected with `RoleServiceError`, and the organization retains exactly one active administrator.

### Organization provisioning now seeds the RBAC roster automatically

The first round's live verification manually seeded Manor's Cremation's RBAC roster with a one-off script — correctly flagged as a gap: every *future* organization provisioned through Phase 20's onboarding flow would have had no roles at all until someone remembered to run the same script by hand. `services/organizationProvisioningService.ts` now wires RBAC seeding into the provisioning workflow itself, at three points:

1. **`startOnboarding` (Step 1)** calls `seedDefaultRoles(organizationId, ...)` unconditionally, immediately after the organization row is confirmed to exist (whether created this call or found from a prior attempt) — before Step 3 can possibly run. Since `seedDefaultRoles`/`seedPlatformDefaultRoles` are already fully idempotent (deterministic ids; a conflict on re-seeding is "already seeded," never an error — see the first round's own section above), calling this on every `startOnboarding` invocation, not only when the organization is brand new, costs a handful of cheap lookups on a retry and nothing more.
2. **`assignInitialAdministrator` (Step 3)** now calls `resolveRoleForKey('administrator', organizationId, ...)` first and refuses (a clear thrown error) if it doesn't resolve. In ordinary operation this never trips — Step 1 already seeded the roster — but it exists as defense in depth against any future call path that might reach this function without going through `startOnboarding` first, rather than silently writing a role assignment that would resolve to zero permissions.
3. **`completeOnboarding`** re-asserts `seedDefaultRoles` (idempotent, a no-op if already seeded) immediately before flipping `organization.status` to `'active'` — "completion before organization activation," guaranteed regardless of which code path actually created the organization, not merely assumed true because Step 1 usually runs first.
4. **`migrateExistingOrganization`** (the backfill path for organizations that predate Phase 20-style onboarding, e.g. Manor's Cremation's own original migration) also now calls `seedDefaultRoles` — so a pre-existing tenant migrated through this path receives the exact same automatic treatment a brand-new one does, closing the "Manor's Cremation must not depend on manual setup that future tenants will not receive" gap directly, including for Manor's Cremation itself if this path were ever re-run.

**Retry-safety.** Every one of these four integration points calls an already-idempotent function; none of them introduce a new lock or new failure mode of their own. A provisioning attempt that fails between organization creation and RBAC seeding (or between RBAC seeding and administrator assignment) is safe to simply retry from the top — `startOnboarding`'s own existing idempotency-key mechanism returns the same organization/session, and the RBAC seeding call that follows completes whatever was left unfinished.

See `services/organizationProvisioningService.test.ts`'s "RBAC provisioning integration" tests: a newly provisioned organization receives all seven default roles; its initial administrator resolves to the full expected permission set; repeated provisioning (retrying `startOnboarding` for the same organization) creates no duplicate RBAC records; a simulated partial failure (organization/session created, RBAC roster removed to simulate an incomplete first attempt) is fully repaired by a retry; existing custom roles and role assignments survive repeated provisioning calls for the same organization; and one organization's provisioning — including creating a custom role — never affects a second organization's roster.

### No cross-request permission cache

The original design cached a resolved permission `Set` per `(identityId, organizationId)` in a process-local `Map`, invalidated explicitly on role/membership changes and organization switch. That cache was only ever correct for a single application instance: any deployment running more than one (multiple processes, multiple serverless invocations, a multi-replica container deployment) could serve a request against one instance's stale cache after a different instance wrote a role change, since nothing ever invalidated the *first* instance's in-memory `Map`. Per the correction's explicit guidance — "removing cross-request caching is acceptable and preferred over weakening revocation correctness" — the cache was removed entirely rather than replaced with a more complex distributed-invalidation scheme. `services/permissionService.ts`'s `resolvePermissions`/`hasPermission`/etc. now always resolve fresh, every call, with zero state shared between calls or instances. See `services/permissionService.test.ts`'s "no cross-request caching" tests, proving a role change takes effect on the very next resolution.

### Durable seeding idempotency

`domain/rbac/deterministicIds.ts` derives every *seeded* row's id from its semantic key — a permission key, a default role key, an `(organizationId, roleKey)` pair — never a random `idFactory` value (custom, user-initiated roles still get one, since there's no "duplicate seed" concept for those). Every seeding insert (`seedPermissionCatalog`, `seedPlatformDefaultRoles`, `seedDefaultRoles`) attempts the deterministic-id insert directly and treats a conflict as "already seeded" rather than erroring, instead of the original "query first, then insert if absent" pattern — which had the same read-then-write race as the admin invariant did. See `services/roleService.test.ts`'s concurrent-seeding tests: three simultaneous `seedPlatformDefaultRoles`/`seedDefaultRoles` calls produce exactly seven roles and exactly seven per-organization enablements, never fourteen or twenty-one.

### Fail-closed role lifecycle behavior

All of the following were already fail-closed by the pre-existing design; this round added explicit tests proving it, and closed the one real gap:

- **A membership referencing a role key that no longer resolves** (deleted, never existed, malformed/garbage input) resolves to an **empty permission set** via `resolvePermissionKeysForRole` — never a fallback to a default or elevated permission set. Tested directly, including adversarial inputs (`'DROP TABLE roles;'`, `'../../etc/passwd'`, empty/whitespace strings).
- **A membership referencing another organization's custom role** also resolves to an empty set — `resolveRoleForKey`'s existing cross-tenant check (a non-null `organizationId` mismatch) applies identically whether the caller is `PermissionService` resolving live traffic or a test constructing the scenario directly.
- **Deleting an assigned custom role** was already refused (`deleteRole` checks every active membership's role first) — now re-checked *inside* the organization lock, closing a real TOCTOU gap where a concurrent assignment landing between an earlier, unlocked check and the actual delete could have let a role be deleted out from under a newly-assigned member.
- **Editing permissions on an assigned custom role** — the one genuine gap this round closed. `updateRole` previously had no admin-invariant check at all: removing `organization.manage` from a role currently held by an organization's only administrator would have silently demoted them. `updateRole` now computes the *hypothetical* post-edit permission set before applying anything, runs it through `countActiveAdminTierMembers`, and refuses the entire update (never a partial application) if it would leave zero administrators.

## Third security-correction round (2026-07-30)

The second round's fencing check had a real gap, identified directly: `assertFenceStillCurrent` and the write it guards are **two separate operations**. A lease can be reclaimed in the gap between them — however small — and once reclaimed, the original holder's already-issued write is not automatically invalidated. Detecting the loss *after* the fact and throwing does not undo a write that already landed. This round closes that gap as far as this project's actual persistence layer allows, and is explicit about the part it cannot close.

### The confirmed Wix Data primitive (empirically verified, not assumed)

Before choosing a design, a throwaway script (`scripts-tmp-verify-wix-revision-occ.ts`, deleted after use — never committed) exercised Wix Data's `items` v2 API directly against a live collection: inserted a row, read it back, updated it, then attempted a second update carrying a deliberately stale "revision" value with obviously-wrong data. The result: `insertDataItem`/`updateDataItem`/`queryDataItems` responses carry **no `revision` field at all**, and a stale value included in an update's request body has **no effect whatsoever** — the stale-tagged update returned HTTP 200 and applied unconditionally; the final read-back confirmed it fully overwrote the row. Wix Data v2's `items` API, as this project accesses it, provides **exactly one atomic primitive**: an insert with an explicit, already-taken id fails with HTTP 409. There is no revision/optimistic-concurrency-control support and no conditional update of any kind. This rules out "confirm and use Wix Data revision/version behavior" outright — there is no such behavior to use.

### The write claim

Given the only real atomic primitive is unique-id insert-conflict, the strongest achievable construction from it is: make **reclaiming a lease structurally impossible while a write is genuinely in flight**, rather than trying to detect a stale write after it happens.

1. Immediately before a protected mutation's actual persistence calls, `commitProtectedWrite` (`services/organizationLockService.ts`) claims a row in a second collection, `organizationRoleWriteClaims` (id = `organizationId`, the same atomic insert-conflict primitive as the lease itself, with its own short TTL, `WRITE_CLAIM_TTL_MS` = 5s). At most one caller can ever hold a live claim for a given organization.
2. The lease's stale-reclaim path (`tryAcquireOnce`) now checks for a live write claim *before* reclaiming an otherwise-expired lease: if one exists and hasn't itself expired, reclaim is refused — treated as ordinary contention, retried like any other acquisition attempt. A lease can never be reclaimed while its holder is provably mid-write.
3. `commitProtectedWrite` re-verifies lease ownership one final time (`assertFenceStillCurrent`) immediately before invoking the actual write, and always releases the claim afterward — success or failure.
4. The claim's own short TTL means a process that crashes while holding it cannot wedge the organization indefinitely — a later acquirer's reclaim attempt sees the claim itself has expired and proceeds.

All five of `RoleService`'s guarded mutations (`assignRole`/`removeRole` via `changeMembershipRole`, `updateRole`, `deleteRole`, `setMembershipStatus`) now route their actual persistence writes through `commitProtectedWrite` rather than calling `assertFenceStillCurrent` separately before a bare write — the exact pattern this round's correction identified as insufficient.

### Honest limitation

This closes the race for the overwhelming majority of the original surface area: a second holder cannot reclaim while a first holder's claim is live. It does **not** achieve mathematically perfect atomicity for the one remaining gap — between `commitProtectedWrite`'s final `assertFenceStillCurrent` check and the moment the actual Wix Data write call is dispatched. No client-side check, however immediate, can close that gap without Wix Data itself supporting a conditional write, which it does not. The only construction that would close this completely is a full event-sourced rewrite of `Membership`/`Role` persistence — deriving "current value" as "the highest-fenced entry," so a late-arriving stale write can physically land but can never become authoritative. This project has not undertaken that rewrite in this phase.

### Stale-writer tests

`services/organizationLockService.test.ts`'s "write claims" suite:
- a live write claim structurally blocks reclaim of an otherwise-expired lease;
- **the exact adversarial sequence**: holder A acquires the lease and passes its final fence check, is paused before its protected write (reproducing the second round's vulnerable "check, then later, separately, write" pattern), the lease is force-expired, holder B genuinely reclaims it and completes its own protected write, A resumes and its stale `commitProtectedWrite` call is rejected (`LockLeaseLostError`) with no state change;
- `commitProtectedWrite` retries the write claim on contention, proceeding only after the holder releases;
- `commitProtectedWrite` fails closed (`LockLeaseLostError`) if the claim can never be acquired within its bounded retry budget.

`services/roleService.test.ts`'s "stale-writer rejection" suite runs the same adversarial sequence against each of the four real write categories, asserting both the rejection and that no state change resulted: a stale role-assignment write, a stale membership-status write, a stale custom-role permission update, and a stale role-deletion write.

## Permission resolution

`resolveRoleForKey(roleKey, organizationId, dataAdapterMode)` is the one function that turns any role key into a `Role` row — alias legacy values first, then look up by key. **Cross-tenant leakage is prevented at this single point**: a resolved role whose `organizationId` is non-null and doesn't match the requesting organization is treated as not found, regardless of how the key was obtained — the same discipline `lib/auth/requireAuthorizedOrganization.ts` already applies to a client-supplied `organizationId`, now applied to a role key too.

## Migration of existing role comparisons

Three real authorization decisions previously compared role names directly, all migrated to policy checks with unchanged behavior, confirmed by the full pre-existing test suite passing unchanged:

- `lib/auth/authorize.ts`'s `hasAdminTierMembership` (mock/wix-mode onboarding-resume gate) now calls `authorizationPolicyService.isAdminTier`, which resolves `organization.manage` instead of comparing to `'owner'`/`'administrator'` literally. Necessarily became `async` (permission resolution is inherently asynchronous); its one call site (`lib/auth/requireOnboardingAccess.ts`) already ran inside an `async` function.
- `services/organizationProvisioningService.ts`'s `countAdminMemberships` (Phase 20's launch-readiness "has an administrator" check) now resolves each active membership's permissions and counts `organization.manage` holders, instead of a literal `role === 'owner' || role === 'administrator'` filter.
- `app/api/auth/invitations/route.ts`'s two `ADMIN_TIER_ROLES.includes(...)` invite gates now call `canInviteUser` (`user.invite`); the invited role's validity is checked via `resolveRoleForKey` instead of a fixed five-value allowlist, so an invitation can now grant any of the seven default roles or an organization's own custom roles, not only the original five.

A fourth pattern — `assignInitialAdministrator` always writing the literal string `'administrator'` when provisioning a new organization's first member — was deliberately **not** migrated: it is a fixed assignment, not a role-name *comparison* or authorization *decision*, and remains exactly as Phase 20 wrote it.

## What this phase deliberately defers

- **No UI to disable one of an organization's seven default-role enablements.** `organizationRoles` is structured to support this (delete the enablement row without touching the shared `roles` row), but no route or UI exposes it — every organization currently has all seven available.
- **No route or UI for "remove a member from the organization."** `RoleService.setMembershipStatus` (added in the security-correction round) already guards this at the service layer — under the organization lock, refusing to disable/remove the last active administrator — so the invariant holds the moment a route is built, rather than depending on that future route remembering to re-implement it. This phase's UI still only covers role *assignment* (`AssignRoleDialog`), not full membership removal — a natural extension of `RoleManagementPanel`/`useOrganizationMembers`, not built here because the spec's own UI list doesn't name it.
- **Custom role permission editing is a flat checkbox matrix**, not a wizard or template gallery — matching this project's standing "deliberately minimal, no granular UI beyond what's asked for" philosophy.
