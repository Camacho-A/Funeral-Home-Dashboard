# Roadmap

## Version 1 — Case Operations (current)

Scope: the four screens visualized in `design/Beacon.dc.html` — Dashboard, Case Detail, Tasks, Reports — backed by Wix Managed Headless for operational data and a small Postgres/object-storage service for compliance documents and the audit trail. Single tenant (Managed Cremations), architected for multi-tenancy from day one. See [PRODUCT_VISION.md](./PRODUCT_VISION.md) for full scope and [ARCHITECTURE.md](./ARCHITECTURE.md) for the technical shape.

Notably, the Reports screen's org switcher in the current design already lists a second, disabled entry — "Gus Camacho Funeral Home — coming soon" — meaning the visual design itself was built anticipating that Beacon would serve more than one funeral home. That expectation is honored structurally (via `organizationId` on every record) well before it's honored functionally.

## Completed: Multi-Tenant Authorization Hardening (Phase 15X)

**Status: closed 2026-07-23.** Originally recorded during Phase 15B's final review — see [ADR-012](./adr/ADR-012-wix-workflow-template-read-integration.md)'s review findings and the former "Known limitations" entry this superseded in `docs/AUTHENTICATION.md`. Full writeup: [ADR-015](./adr/ADR-015-multi-tenant-authorization-hardening.md).

**The gap (now closed):** none of the Route Handlers introduced by the Wix read integrations verified that the `organizationId` in the request actually belonged to the caller's authenticated session — `organizations`, `workflow-templates` (both routes), `cases` (both routes), and `tasks` all trusted a path/query parameter directly. As public HTTP endpoints with no middleware coverage (`middleware.ts`'s matcher deliberately excludes `/api/*`), any HTTP client — authenticated or not — could call any of these six routes with a forged `organizationId` and receive that organization's data.

**Resolution:** a single reusable helper, `lib/auth/requireAuthorizedOrganization.ts`'s `requireAuthorizedOrganization(requestedOrganizationId)`, composes the already-existing, already-tested `resolveAuthorizationContext` (Phase 13) with session resolution and a standardized `401`/`403` `NextResponse`. All six Route Handlers now call it before using `organizationId` for anything, and use only the returned, trusted `context.organizationId` downstream. See ADR-015 for the full design, the architecture-review findings that preceded implementation, and what remains explicitly deferred (real Wix-backed membership data, still mock-fixture-only; Phase 16 write endpoints must reuse this same helper rather than re-deriving authorization inline).

## Completed: Wix Write Integration (Phase 16)

**Status: closed 2026-07-23.** Full writeup: [ADR-016](./adr/ADR-016-wix-write-integration.md).

**The gap (now closed):** `casesService.create/update` and `tasksService.create/update/remove` were mock-only — a case or task created/edited while `DATA_ADAPTER=wix` never persisted to Wix, so it never appeared in a subsequent Wix-sourced read (documented in ADR-013/014). Real Wix writes now exist for case create/update and task create/update/delete, all reusing Phase 15X's `requireAuthorizedOrganization` — no new authorization logic was written. `lib/wixDataApi.ts` gained `insertWixDataItem`/`updateWixDataItem`/`deleteWixDataItem`; `lib/wixCaseMapper.ts`/`lib/wixTaskMapper.ts` gained matching write-side build/validate/merge functions; four Route Handlers were added or extended (`POST /api/cases`, `PATCH /api/cases/[caseId]`, `POST /api/tasks`, and a new `app/api/tasks/[taskId]/route.ts` for `PATCH`/`DELETE`).

**Remaining, explicitly deferred (unchanged by this phase):** `createdBy`/`intakeOwnerId` still derive from `hooks/useSession.ts`'s hardcoded stub, not a real server-resolved identity — Identity Model Hardening remains open (**closed in Phase 30** — see below; `POST /api/cases` now resolves both server-side via `resolveStaffProfileForCaller`, never the client body). Real Wix-backed `organizationMemberships` reads (Phase 15X's own deferred item) are also still outstanding — both are prerequisites for a genuine second organization to operate through this app, not just exist in fixtures.

## Completed: New Case UX Polish and Initial Note (Phase 16A)

**Status: closed 2026-07-24.** Full writeup: [ADR-017](./adr/ADR-017-new-case-ux-polish-and-initial-note.md).

Uppercase transform, MM/DD/YYYY and MM/YY input masks with real calendar/month validation, and a show/hide toggle for card fields (replacing permanent unmasking) were added to the New Case form (`utils/inputMask.ts`, `components/modals/NewCaseModal.tsx`). ## Completed: Case Number Generation (Phase 16B)

**Status: closed 2026-07-23.** Full writeup: [ADR-018](./adr/ADR-018-case-number-generation.md).

Every case now has a permanent, human-facing `B{YYYY}-{###}` identifier (e.g. `B2026-001`), always server-generated and read-only, displayed prominently on Case Detail and in every case list/table, and searchable from the global search bar. Mock-mode generation is a simple scan of existing fixtures (safe — single-threaded); Wix-mode generation uses a new `caseSequences` collection and an atomic `INCREMENT_FIELD` patch, empirically verified against the live Wix project to be race-free under concurrent case creation, with a race-safe bootstrap path for a year's first case. Case Numbers are never reused — Beacon's existing soft-delete-only model (cases are never hard-deleted) already guarantees this structurally, with no new code needed for that guarantee.

**Deferred, unchanged by this phase:** case notes still have no Wix write path (Phase 16A's own reported gap); identity model hardening remains open (Phase 16's own reported gap).

## Completed: Workflow Management (Phase 18)

**Status: closed 2026-07-23.** Full writeup: [ADR-019](./adr/ADR-019-workflow-management.md).

The first real admin surface for workflow templates: a new `/settings` page (activating the Sidebar's previously-inert "Settings" entry) lists an organization's templates and lets an admin view every version's stages/checklist items and edit an existing stage's label, SLA target, attention flag, and checklist item labels, plus reorder stages. Every edit is saved via a new `POST /api/workflow-templates/[templateId]/versions`, which always **inserts** a brand-new `WorkflowTemplateVersion` — historical versions are never modified, and existing cases keep resolving against their own `Case.workflowSnapshot` exactly as before (both guarantees were already structurally true; this phase's write path simply never violates them). `workflowTemplateVersions`' previously-aspirational "insert-only, application-enforced" contract (`docs/WIX_DATA_SCHEMA.md`) is now genuinely enforced by the one code path that writes to it.

**Deferred, unchanged by this phase:** adding/removing a stage or checklist item; editing intake fields, case types, or a template's own name/enabled flag; reordering that preserves a combined display stage; full optimistic-concurrency retry for version-number races (a same-version collision 409s once rather than auto-retrying, per the ADR's own reasoning on why that's proportionate here).

## Completed: Configurable Intake Form Builder (Phase 19)

**Status: closed 2026-07-23.** Full writeup: [ADR-020](./adr/ADR-020-configurable-intake-form-builder.md).

The New Case intake form is now fully data-driven. `IntakeFieldTemplate` gained `fieldType` (13 supported types), `required`, `defaultValue`, `displayOrder`, `uppercase`, `masked`, `multiline`, `validationType`, and `options` — every property optional, so every pre-existing field (mock fixture and the real Wix template) keeps working with zero migration. `components/modals/NewCaseModal.tsx` no longer hardcodes per-field behavior by literal key name (the old `UPPERCASE_FIELD_KEYS`/`DATE_FIELD_KEYS`/`EXPIRY_FIELD_KEYS` are gone) — it renders and validates purely from each field's own resolved configuration. The Workflow Editor (Phase 18) gained a matching intake-field builder: add/edit/delete/reorder fields, all saved as part of the same new `WorkflowTemplateVersion` as any stage edits. No changes to `Case`, `NewCaseInput`, or the Wix `cases`/`workflowTemplateVersions` schemas were needed — configurable fields either map to an existing structured `Case` property or land in the pre-existing `fieldValues` bucket, exactly as before.

**Deferred, unchanged by this phase:** adding/removing an intake section (only fields within an existing section); editing the template's own name/`isEnabled`/`caseTypes`; live input masking for phone/currency (validation only, no auto-formatting); Phase 18's own deferred items (stage/checklist-item add/remove, combined-display-stage-aware reordering).

**Security follow-up flagged, not implemented (see ADR-020's own section):** payment field (`cardNumber`/`cardExp`/`cardCvv`) persistence is unchanged by this phase and remains a real gap — values are stored as plaintext in `Case.fieldValues`, CVV is retained indefinitely, and the new `masked` property is a UI-only affordance with no encryption or PCI protection behind it. Full card data should eventually route through a PCI-compliant payment provider and be stored only as a token/reference; until then, any new logging/analytics/error-reporting work must explicitly exclude masked/payment fields.

## Completed: Payment Data Containment & Secure Payment Architecture (Phase 19A)

**Status: closed 2026-07-23.** Full writeup: [ADR-021](./adr/ADR-021-secure-payment-architecture.md).

Closes the security follow-up flagged (not fixed) by Phase 19/ADR-020, plus a second, independent leak found on Case Detail. `IntakeFieldType` drops `'creditCard'`/`'expiration'`/`'cvv'` entirely (also removed from `IntakeValidationType`, closing a back door where an admin could reconstruct card validation via `fieldType: 'text', validationType: 'creditCard'`) and gains one new type, `'payment'` — an entire secure section (`label`/`required`/`paymentPurpose`/`paymentAmount`/`paymentDescription`), never a data-entry control an admin can wire to `checklistItemIndex`/`mapsToCaseField`. `domain/workflow/resolveIntake.ts`'s `buildIntakeFieldValues`/`buildStructuredCaseFields` now unconditionally skip any `'payment'` field as a hard, defense-in-depth guarantee, independent of `components/modals/NewCaseModal.tsx`'s own isolation (a payment field's five sub-values live in an entirely separate, uncommitted local state, cleared on every submit/cancel/close, never written to `draft`). A new `lib/paymentFieldGuard.ts` rejects any request body naming a raw card field outright (400, before any other processing) in `POST /api/cases`, `PATCH /api/cases/[caseId]` (both the body and the nested `patch`), and the workflow-template version endpoint's field validation — mandatory server-side enforcement, not reliant on the client. Case Detail's independent leak (checklist item 8's password-masked free-text box, present regardless of what the intake form did) is closed by relabeling it `"Payment collected"`, a plain checkbox confirmation with `hasField: false`. A provider-neutral `PaymentRecord` type (`types/payment.ts`) documents the shape a real future integration (Stripe/Square/Wix Payments) will populate — not wired into anything yet, per this phase's explicit scope (containment and architecture, not a provider integration). The live Wix Standard Cremation Workflow template was migrated (a new, additive `workflowTemplateVersions` row) to the new `'payment'` field shape, and manually verified end-to-end against the live Wix environment: a case created with card data entered has zero payment data anywhere in the stored Wix record, confirmed directly via the Wix Data API; all verification cases were deleted afterward.

**Deferred, unchanged by this phase:** no real payment provider is integrated — `PaymentRecord` is documentation-only; a future phase will need to actually wire a provider's client-side SDK (Stripe Elements, Square Web Payments) and a small server-side confirmation endpoint that populates `PaymentRecord` fields, never PAN/CVV/expiration.

## Completed: Clover Hosted Checkout Integration (Phase 19B)

**Status: closed 2026-07-24** (Clover sandbox connection pending real credentials — see below). Full writeup: [ADR-022](./adr/ADR-022-clover-hosted-checkout-integration.md).

Phase 19A's deferred item, resolved: `PaymentRecord` is now a real, persisted type (`paymentRecords` Wix collection) and a new `PaymentIntegration` type holds organization-scoped provider configuration (`paymentIntegrations` collection) — both created live via the Wix Data API, additive only. `lib/paymentProvider.ts` defines a provider-neutral interface (`createCheckoutSession`/`verifyWebhook`/`getPaymentStatus`/`mapProviderPayment`); `lib/clover/*` is its first implementation. Staff can now click "Collect with Clover" on Case Detail's new `PaymentCard` (replacing Phase 19A's transient browser-only card-entry section in the New Case form, now purely informational), which creates a Hosted Checkout session server-side (`POST /api/cases/[caseId]/payments/clover/checkout` — authorized, case-ownership-checked, amount-validated, idempotent) and redirects the full browser to Clover's own hosted page; no card input of any kind is ever rendered by Beacon. A signed webhook (`POST /api/webhooks/clover`, HMAC-SHA256-verified against `Clover-Signature`, organization/merchant-isolated, idempotent and order-tolerant) is the sole authoritative source for "did this payment succeed" — the browser's own return-redirect only triggers a status poll (`/cases/[caseId]/payments/return`), never a direct success claim. A verified successful payment marks `Case.paymentStatus` paid and the "Payment collected" checklist item done, without ever auto-advancing the workflow stage. Multiple payments per case are supported by design (one `PaymentRecord` row per attempt, never a singleton). Full test coverage (auth/cross-org, invalid amount, idempotent checkout creation, valid/invalid/duplicate/out-of-order webhook signatures, safe-metadata-only persistence, mock adapter behavior) using a fake Clover transport — no live Clover API is called by the automated suite.

**Correction passes (same day):** three gaps were flagged after review and closed before final approval — see ADR-022's own "(correction pass)" sections. (1) Concurrent duplicate checkout attempts are now prevented by a real, atomically-enforced Wix unique index (`paymentRecords.idempotencyKey`, composed as `{organizationId}:{clientKey}` since Wix Data doesn't support genuine multi-field unique indexes), replacing an application-level scan that could race under concurrency; a live empirical test also caught that `providerCheckoutId`'s original unique index would have rejected a second pending payment sharing an empty placeholder value, fixed by seeding a per-record placeholder instead. (2) Webhook delivery dedup is now durable and cross-instance via a new `webhookEvents` collection. (3) A follow-up correction found that dedup's first version conflated *claiming* an event with *completing* it — if the downstream payment update failed after the fingerprint was claimed, every later retry would be silently swallowed. `webhookEvents` gained a full `processing`/`completed`/`failed` lifecycle (`attemptCount`/`firstReceivedAt`/`lastAttemptAt`/`completedAt`), so a failed attempt is retried (not dropped), a stale abandoned claim is reclaimed, concurrent-in-flight processing is never duplicated, and a database failure during the claim itself is never mistaken for success. Also renamed the sandbox env var references to `CLOVER_MANORS_SANDBOX_*` (explicitly distinguishing them from a future production set) and folded `merchantId` into the same env-var-reference pattern as the other two Clover secrets.

**Required before this integration is actually usable:** Manor's Cremation's `paymentIntegrations` row exists in live Wix but is `isEnabled: false` with empty reference values — no real Clover sandbox merchant credentials were available during this phase. Activating it requires: a real Clover sandbox (or production) merchant account, setting `CLOVER_MANORS_SANDBOX_MERCHANT_ID`/`CLOVER_MANORS_SANDBOX_PRIVATE_KEY`/`CLOVER_MANORS_SANDBOX_WEBHOOK_SECRET` as server-only env vars, configuring the webhook URL in Clover's Merchant Dashboard, and flipping `isEnabled` to `true` — no code change needed. Manual sandbox verification (the full redirect → pay → webhook → verified-paid-status flow against a real Clover sandbox) has not been performed for the same reason and remains outstanding.

## Completed: Service Catalog, Case Order & Pricing Engine (Phase 19C)

**Status: closed 2026-07-24.** Full writeup: [ADR-023](./adr/ADR-023-case-order-pricing-engine.md).

Replaces Phase 19B's manually-entered payment amount with an itemized `CaseOrder`, calculated entirely server-side. A new `serviceCatalog` collection (created live, seeded with Manor's Cremation's five v1 services — Direct Cremation $890; weight surcharges at 201–250/251–300 lb; Extra Death Certificate; Mail Cremated Remains) is the one source of prices `domain/pricing/calculateOrder.ts` reads through — no service code or price is ever hardcoded in a component. `CaseOrder`/`CaseOrderLineItem` (also created live) are append-only/versioned exactly like `WorkflowTemplateVersion`: editing a case's services supersedes the current version and creates a new one, so a `PaymentRecord`'s `caseOrderId` reference and that version's own totals never change retroactively. A fourth collection, `caseOrderAuditEntries` (added beyond the phase's own three-collection list, for the same reason Phase 19B added `webhookEvents`), records every edit — user, timestamp, action, previous/new value, and the exact dollar delta, in the same "Changed: Weight, Under 200 lb → 201–250 lb, +$290" format the phase's own spec used as an example.

The New Case form's "Services & Charges" section (`components/case/ServicesAndChargesSelector.tsx`, shared with the new "Edit Services" modal on Case Detail) shows a live itemized summary as staff select services — computed by the *same pure function* the server later uses to calculate authoritatively, but never trusted from the browser: only raw selections (weight tier, quantities, checkboxes) are ever submitted, never a total, and the server always re-fetches the catalog and recalculates independently before persisting anything. `components/case/PaymentCard.tsx` is retired, replaced by `components/case/CaseOrderCard.tsx` (itemized services, balance, status, payment history, Edit Services/Collect Balance with Clover/Print Order); the Clover checkout route was corrected to reject any client-supplied `amount` outright and instead always charge the case's own `CaseOrder.balanceDue`. Multiple payments against one balance are supported: a case's balance nets out every succeeded payment across all of its order's versions, and `markCasePaidIfVerified` now only marks a case fully paid once that balance actually reaches zero (a case with no CaseOrder — pre-Phase-19C data — keeps Phase 19B's original single-payment-means-paid behavior, unchanged and re-verified).

**Deferred, unchanged by this phase:** discount/tax support (`calculateAdjustment`/`discountTotal`/`taxTotal` exist as tested, ready-to-call functions/fields, but no UI produces a non-zero value — nothing in this phase's own mockups called for one); the actual Revenue/Services-Sold/Weight-Surcharge/Average-Case-Value report *views* (the underlying itemized, versioned data is now structured to support them, per this phase's own "Reporting" section, but building the reports themselves was explicitly future work); a catalog-management admin UI (Manor's five rows were seeded directly via the Wix Data API, same as every other one-tenant seed in this project's history — an org wanting to add/reprice a service today needs a direct Wix Data edit, not an in-app settings screen).

## Completed: Organization Onboarding & Tenant Provisioning (Phase 20)

**Status: closed 2026-07-24.** Full writeup: [ADR-024](./adr/ADR-024-organization-onboarding-tenant-provisioning.md).

Builds the path a second (third, fourth, ...) funeral home takes from nothing to a fully provisioned, launch-ready Beacon tenant — every previous phase's live-Wix seeding for Manor's Cremation was done by hand via direct `curl` calls; this phase makes that repeatable, versioned, and idempotent through application code. A new `OnboardingSession` (`not_started`/`in_progress`/`blocked`/`completed`, nine ordered steps) tracks progress independently of `Organization.status` (`draft` → `onboarding` → `active`), which is new itself — the pre-existing `isActive` boolean is kept in sync rather than replaced, so every existing caller (`lib/auth/authorize.ts` most notably) is unaffected. `services/organizationProvisioningService.ts` provisions everything a tenant needs (primary location, initial administrator membership, an organization-owned workflow — starter, cloned-by-value, or minimal — its seeded intake, its own service catalog, a disabled Clover placeholder naming only credential-reference names, branding) with every step idempotent: retrying never duplicates a tenant, a location, a membership, a workflow, or a catalog. `POST /api/onboarding/start` is gated by a new, deliberately minimal "platform administrator" concept (`PLATFORM_ADMIN_USER_IDS`, an env-var allowlist — not a new role); every other onboarding route accepts only an opaque `onboardingSessionId`, never an `organizationId`, resolving the real organization server-side before deciding whether the caller (the platform admin who started it, or an already-assigned organization administrator) may act on it. `POST /api/onboarding/complete` independently re-validates every required piece of provisioned state before activating anything — a client's claimed progress is never trusted on its own.

The existing `organizations` Wix collection (read-only since Phase 15A) was extended in place with nine new profile fields rather than duplicated; four new collections (`organizationLocations`, `onboardingSessions`, `organizationBranding`, `onboardingAuditEntries`) were created live. Manor's Cremation's own migration ran live the same day: its organization row was backfilled (never overwriting its existing `name`/`isActive`), a primary location was created (it never had one), and its existing workflow/service catalog/Clover integration were confirmed and linked, never recreated — recorded via a `completed` onboarding session and an audit entry.

**Deferred, unchanged by this phase:** logo file upload (`logoUrl` accepts only a hosted URL; no object-storage integration exists yet); email invitations for a newly-assigned administrator with no existing Beacon/Wix identity; a genuine cross-organization "approved template" policy (today, any existing template id can be named as a clone source); a catalog-/workflow-management admin UI (same pre-existing gap Phase 19C already left open).

## Completed: Identity, Authentication & Session Management (Phase 21)

**Status: closed 2026-07-25.** Full writeup: [ADR-025](./adr/ADR-025-identity-authentication-architecture.md).

Beacon's own email/password identity system — a new, additive `AUTH_ADAPTER='identity'` value alongside the unchanged `'mock'`/`'wix'` modes. Email/password login with remember-me, forgot/reset/change password, email verification, invitations (an invitation is a `Membership` row with `status: 'invited'` — no dedicated collection), MFA (TOTP enrollment/verification/recovery codes — architecture complete; the two-step login-time *challenge* is deferred, see below), full session lifecycle (view/revoke individual sessions, sign out everywhere, sliding expiration, device tracking), organization switching for multi-membership identities, and login-activity-driven brute-force lockout. `Identity` (who someone is) and the new `Membership` model (what they may do in an organization) remain deliberately separate types, coexisting with — never replacing — the pre-existing mock-fixture-based `OrganizationMembership` model that `'mock'`/`'wix'` sessions keep using unchanged. A revocable session registry (`IdentitySession`) sits alongside the existing stateless signed cookie, since a JWT alone can't support revocation, "sign out everywhere," or device listing.

Five new Wix collections (`identities`, `sessions`, `emailVerificationTokens`, `passwordResetTokens`, `loginActivityEvents`) were created live; the existing `organizationMemberships` collection (created empty back in Phase 14A, never previously written to) was extended in place to serve both the legacy and new membership row shapes side by side — a live schema collision discovered and resolved (with the user's explicit input) during this phase's own verification step, not assumed away. Existing mock/wix users were migrated into the new model live (idempotent, re-run and confirmed to create nothing new the second time) with no forced password resets (a migrated identity has no password until they set their first one via forgot-password) and no memberships lost (an inactive legacy membership becomes a `disabled` `Membership` row, not a dropped one).

A post-approval security review (2026-07-25/26) added three corrections before this phase's own commit: an `IdentityMessageSender` abstraction (test/dev/production-failing adapters) replacing every route that used to return a raw password-reset/verification/invitation token directly in its response; explicit `Origin`/`Host` CSRF verification (`lib/auth/csrf.ts`) added to every cookie-authenticated, state-changing Route Handler across the whole app (not just this phase's own routes); and rotation of a live demo credential that had briefly been disclosed during manual verification.

**Deferred, unchanged by this phase:** the MFA login-time challenge step (enrollment/verification/recovery-code consumption are fully built; the two-step *login* UX is not — redirects with `mfa_required` instead); transactional email (no provider is wired up anywhere in this codebase; reset/verification/invitation tokens are delivered via `IdentityMessageSender` rather than emailed); unifying `StaffProfile` and `Identity` into one directory (same pre-existing gap Phase 20 already left open, for `OrganizationMembership`/`Membership`) — **closed in Phase 30**, see [ADR-034](./adr/ADR-034-identity-model-hardening-and-staff-assignment-architecture.md).

## Completed: Role-Based Access Control (Phase 22)

**Status: closed 2026-07-27 (architecture); first security-correction round closed 2026-07-28; second security-correction round closed 2026-07-29; third security-correction round closed 2026-07-30.** Full writeup: [ADR-026](./adr/ADR-026-role-based-authorization-architecture.md).

Replaces every hardcoded role-name comparison (`role === 'owner' || role === 'administrator'`, repeated across `lib/auth/authorize.ts`, `services/organizationProvisioningService.ts`, and `app/api/auth/invitations/route.ts`) with a centralized permission model, without changing what any of those decisions actually grant. Authorization now flows Authenticated Principal → Identity → Membership → Assigned Role → Resolved Permissions → Authorization Policy → Business Operation: `services/roleService.ts` owns role lifecycle (seed/create/clone/update/delete/assign/remove/setMembershipStatus), `services/permissionService.ts` resolves a role key to its permission set (always fresh — no cross-request cache), and `services/authorizationPolicyService.ts` is the only layer any Route Handler or business service calls (`canEditCase`, `canCollectPayment`, `canManageOrganization`, ...) — no business service compares a role name or inspects `AUTH_ADAPTER`.

Seven platform-default, organization-scoped roles (Administrator, Manager, Funeral Director, Arranger, Office Staff, Accounting, Read Only; 22 permissions across 10 resources) are seeded once globally and enabled per organization; organizations may clone a default role into their own renamable, re-permission-able custom role, but platform defaults themselves remain immutable. `Membership.role`/`AuthorizationContext.role` were widened from a closed five-value union to a plain role key — the one change touching an existing field — with every legacy value (`owner`/`administrator`/`caseManager`/`staff`/`readOnly`) aliased onto the equivalent new default role (`domain/rbac/legacyRoleAliases.ts`), so no existing membership row needed to change and no existing authorization outcome changed, confirmed by the full pre-existing test suite passing unchanged throughout.

Seven new Wix collections (`permissions`, `roles`, `rolePermissions`, `organizationRoles`, `organizationRoleAuditEntries`, `organizationRoleLocks`, `organizationRoleWriteClaims`) were created live and seeded with the full permission catalog, the seven default roles and their grants, and Manor's Cremation's own role enablement roster and existing administrator's role assignment carried forward unchanged. New UI: an Organization Roles Page (role list, Role Editor with an interactive Permission Matrix, Assign Role Dialog, and a Permission Inspector showing the current session's own resolved permissions), linked from the top bar alongside Security for `AUTH_ADAPTER='identity'` sessions.

**First security-correction round (2026-07-27/28)** closed five gaps before final approval: the last-administrator invariant was made concurrency-safe via a durable per-organization lock (`services/organizationLockService.ts`, backed by the new `organizationRoleLocks` collection) plus a single unified admin-count check run inside it by every mutation that can affect who counts as an administrator; the cross-request permission cache was removed entirely (it was only ever correct for a single application instance); seeding was made durably idempotent under concurrency via deterministic ids; fail-closed behavior for missing/foreign/malformed roles was confirmed by test and one real gap (permission removal from an assigned custom role) was closed; and a permission/resource count discrepancy was corrected (22 permissions, 10 resources).

**Second security-correction round (2026-07-29)** closed two further production-integrity gaps: the lock became a renewable lease with ownership-token validation and a monotonic fencing token (the original flat TTL permitted a second owner to reclaim the lock mid-operation under realistic Wix Data rate-limiting conditions this project hit live); and RBAC seeding was wired directly into organization provisioning (`startOnboarding`/`assignInitialAdministrator`/`completeOnboarding`/`migrateExistingOrganization`), so every newly provisioned or migrated tenant automatically receives its default-role roster — Manor's Cremation no longer depends on the one-off manual seeding script that provisioned it during this phase's own live verification.

**Third security-correction round (2026-07-30)** closed the remaining fencing gap identified in the second round: a bare `assertFenceStillCurrent` check immediately before a write is still two separate operations, and a lease could be reclaimed in the interval between them. Empirically confirmed live (then deleted, never committed) that Wix Data's `items` API has no revision/optimistic-concurrency support whatsoever — a stale value in an update request is silently ignored. The strongest achievable fix given that constraint: a second, short-lived **write claim** (new `organizationRoleWriteClaims` collection) taken atomically immediately before a protected write, which the lease's own reclaim path now checks — a lease cannot be reclaimed while a write is genuinely in flight. All five guarded mutations now route through `commitProtectedWrite` rather than a bare fencing check. One gap is explicitly documented as not fully closable without either Wix Data conditional-write support or a full event-sourced rewrite of `Membership`/`Role` persistence — neither undertaken this phase.

**Deferred, unchanged by this phase:** disabling one of an organization's seven default-role enablements (the `organizationRoles` roster supports it; no route/UI exposes it); anything beyond a flat checkbox permission-editing UI for custom roles. ("A full 'remove a member from the organization' flow" — closed by Phase 23, below.)

## Completed: Document Generation & Template Management (Phase 25)

**Status: closed 2026-08-05.** Full writeup: [ADR-029](./adr/ADR-029-document-generation-and-template-management.md).

## Completed: Electronic Signatures & Authorization Workflows (Phase 26)

**Status: closed 2026-08-14.** Full writeup: [ADR-030](./adr/ADR-030-electronic-signatures-and-authorization-workflows.md).

This phase also **resolved** ADR-029's own documented gap around adding a secondary index to an existing Wix Data collection (the correct endpoint is a top-level `POST/GET/DELETE https://www.wixapis.com/wix-data/v2/indexes` resource, not nested under `/collections/{id}`), and used the fix to retroactively provision the seven secondary indexes Phase 25's three collections had been missing since their creation.

**Deferred, unchanged by this phase (explicitly out of scope):** SMS verification, identity-verification providers, notarization, DocuSign/Adobe Sign integration, workflow automation, OCR, AI document processing, family portal, an advanced notification platform. ## Completed: Scheduling & Resource Management (Phase 27)

**Status: closed 2026-08-03.** Full writeup: [ADR-031](./adr/ADR-031-scheduling-and-resource-management.md).

Builds the scheduling platform ADR-030 and the merge engine's own reserved `case.service.date`/`case.service.location` fields had been anticipating: arrangement conferences, viewings, visitations, funeral and graveside services, witness cremations, crematory and cemetery appointments, and staff/internal meetings, each coordinating a case with staff, chapels, viewing rooms, vehicles, and equipment. ## Completed: Family Portal & External Collaboration (Phase 29)

**Status: closed 2026-08-05.** Full writeup: [ADR-033](./adr/ADR-033-family-portal-and-external-collaboration.md).

Builds the first external-facing (non-staff) authenticated surface in Beacon: a `/family` portal letting a case's next of kin and other authorized relations view case status, download family-visible documents, complete e-signature requests, view and pay balances, view appointments, and message staff. Business logic underneath (documents, signatures, payments, scheduling reads) reuses existing services almost entirely unmodified through thin wrapper services (`services/portal/portal*.ts`), each returning only explicit, allowlisted DTOs — never a raw internal domain type. Two small, additive, backward-compatible changes touch already-shipped code: `signatureService.ts`'s completion/decline functions gained an optional `ctx?` parameter (default preserves the existing `/sign` flow unchanged); `notificationService.ts` gained a `portal_user` recipient scope and an email-resolution fallback for the new, non-`Identity` population. The already-shipped staff Clover checkout route was deliberately left untouched — a new `paymentsService.initiateCheckout()` function was extracted instead, avoiding any regression risk in a financial flow nobody asked to change. Family-initiated activity is attributed via the same anonymous-actor pattern `signatureService.ts` already established for external signers (`actorIdentityId: null`, real attribution carried in `metadata`), never conflating `PortalUser`'s id-space with `Identity`'s.

Security posture: a fully isolated family session (distinct cookie, distinct signing-key derivation, distinct token audience, a dedicated `/family/*` branch in `middleware.ts` that never touches the staff cookie), existence-hiding on every credential-adjacent route, `caseDocuments.familyVisible` defaulting to `false` unconditionally with exactly one staff-gated mutator, and a new in-memory rate limiter (`lib/rateLimiter.ts`, explicitly named as process-local — the same class of gap already disclosed for staff login) applied to login, invitation acceptance, messaging, and payment checkout. `lib/auth/sessionIsolation.test.ts` proves the isolation both cryptographically and structurally (a source-tree walk confirming no family route imports a staff auth resolver and vice versa).

Five new Wix collections (`portalUsers`, `portalInvitations`, `portalAccess`, `portalSessions`, `portalMessages`) were created and live-verified — a full invitation→acceptance→access→session lifecycle, the critical `(portalUserId, caseId)` resolution lookup, cross-case isolation (fails closed), bidirectional messaging, and revocation (fails closed) — all confirmed against Manor's Cremation's real, existing organization and a real case, with every disposable row deleted and zero residual confirmed afterward. `caseDocuments` was extended live with `familyVisible`, surfacing a previously-undocumented requirement (the schema-update `PUT` needs the collection's current `revision` explicitly) now recorded for future phases. Two new staff RBAC permissions (`portal.manage`, `portal.message`) bring the catalog to 44.

**Deferred, unchanged by this phase (explicitly out of scope):** family self-registration, document uploads or case-data edits by family, appointment rescheduling, live chat/message editing/deletion, SMS/push for the family surface, native mobile apps, external identity verification, AI. The Clover webhook does not yet distinguish a family-initiated payment from a staff-initiated one. One person holding both a staff `Membership` and a `PortalAccess` simultaneously is unsupported.

## Completed: Real Notification Delivery (Phase 33)

**Status: closed 2026-08-12.** Full writeup: [ADR-037](./adr/ADR-037-real-notification-delivery.md).

Makes Beacon's notification platform (Phase 28, all delivery simulated ever since) actually deliver: a production email provider (Resend) backing both `IdentityMessageSender` (mandatory security flows) and `EmailProvider` (preference-respecting notifications) through one shared `lib/email/resendClient.ts`, a new staff-only SMS channel (Twilio, gated by a new `Identity.phone` field), and the digest-batching/quiet-hours preference fields that had sat schema-only and unenforced since Phase 28. A fully-configured real provider wins regardless of `NODE_ENV`, so real sending can be opted into locally, matching Clover's own sandbox-flag posture.

Closed the background-job gap named as a blocker three separate times across Phases 27/28/31 (`SchedulingNotifier`, digest/quiet-hours enforcement, `INVOICE_OVERDUE`) with the smallest primitive that unblocks it: Vercel Cron. A new `vercel.json` + `CRON_SECRET`-gated `POST /api/cron/notification-digest` runs `notificationDigestService.ts`'s sweep every 15 minutes — the one deliberate, documented exception to this codebase's otherwise-universal "every query is organization-scoped" rule (a cron-triggered sweep has no per-request organization to scope to), structurally contained to a single call site by a new test. `SchedulingNotifier`/`INVOICE_OVERDUE` remain unbuilt — each has its own trigger semantics to design, not reused speculatively just because the primitive now exists.

Live Wix verification surfaced a real, previously-undiscovered defect — again, exactly what live verification is for: `lib/wixNotificationDeliveryMapper.ts`'s channel/status allowlists were never updated for the widened `NotificationChannel`/`DeliveryStatus` unions, so `mapWixNotificationDeliveryItem` silently dropped every real `'sms'` or `'queued_for_digest'` row read back from Wix — invisible to every mock-mode test, since mock mode never round-trips through this mapper. First surfaced when the digest sweep reported zero groups against a row it had just confirmed existed via a direct query. Fixed and re-verified end to end: a disposable digest-eligible delivery correctly flushed, the delivery's status flipped to `'sent'`, and the cron route's auth gate was confirmed live (401 on missing/wrong secret, 200 and a real sweep on the correct one) — everything cleaned up afterward with a final residual check confirming zero leftover rows. This live pass also corrected, not merely extended, every prior phase's documented "resend the full field list via `PUT`" schema-extension mechanism: that endpoint returns a bare 404 for both collections touched this phase; the confirmed-correct primitive is `POST /wix-data/v2/collections/create-field`, one field per call.

No new RBAC permission keys — every field this phase activates is a personal, per-identity preference. Catalog stays at **54**, unchanged from Phase 32.

**Deferred, unchanged by this phase (explicitly out of scope):** push notifications (no PWA/service-worker infrastructure exists); webhooks (a distinct "integrations" feature); `SchedulingNotifier`/`INVOICE_OVERDUE` real triggers (unblocked, not built); real SMS to family/`PortalUser` recipients (no phone field, no consent-capture flow — real email to family is a side effect of this phase, since the existing `portal_user` fallback already called the same email path); per-organization notification policy defaults (`notification.admin` stays reserved); a per-channel digest frequency for SMS.
